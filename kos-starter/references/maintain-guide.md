# maintain-guide — Mode 3 GROW 养护与沉淀

> 触发：「体检」「养护」「知识库乱了」「项目完结提炼」「迁移知识库」，或 Mode 2 的成长触发条件命中。
> 原则：养护不是改造——库的结构从 BUILD 起就是完整的四区，GROW 管的是**账实一致、内容健康、知识沉淀、平滑迁移**。所有动作先提议、用户确认再执行。

## 养护机制总览

| 机制 | 干什么 | 何时 |
|---|---|---|
| 对账脚本 | 索引↔文件账实核对，只读出报告 | 每批操作收尾 + 体检时 |
| 事件驱动对账 | 批量操作收尾当场跑脚本、当场修 | 每次导入 / 迁移 / 清理 / 挂载 |
| 30 天体检 | 结构层 + 内容层全面检查 | 每 30 天，或体感变差时 |
| 纠偏即规范 | 纠正过的说法当场固化成规范文件 | 第二次遇到就固化 |
| AI 主动回填 | 协作中的新理解提议回填进库 | 协作中随时 |
| 项目完结提炼 | 项目域归档冻结 + 方法论沉淀 | 产品线完结 / 阶段性完结 |
| 换机迁移 | 迁移清单打包、新机还原验证 | 换电脑时 |

## 对账脚本（没有就让 AI 现场写一个）

让 AI 当场写一个只读检查脚本，语言不限（用户环境能跑即可，PowerShell / Python / Bash 都行），核对四件事：

1. 索引列的文件都存在
2. 存在的文件都在索引里
3. 断链：索引或正文引用了不存在的文件
4. 孤儿引用：没有任何索引指向的文件

脚本只输出报告，不改任何文件——修不修、怎么修，人决定。脚本存进库（如 `tools/` 目录）并登记索引，之后复用。

**脚本自检（写完必做，防误报漏报）**：临时造两个测试项——库里放 1 个不登记索引的孤儿文件，索引里写 1 个不存在的文件名——跑一遍脚本，两项应双双出现在报告里；验证通过后删掉测试项。小白没有代码审计能力，这步就是脚本的可信度证明——拿着未经自检的报告去「当场修」，比不修还危险。

## 事件驱动对账

每批操作（入库、迁移、清理、挂载预置包）收尾时跑一遍脚本，发现项当场修——不攒大扫除，攒到月底的账没人对。

## 30 天体检（两层）

- 结构层：跑对账脚本，看报告处理发现项
- 内容层：人工 + AI 一起过——过时结论、前后矛盾、断链积压、该晋升没晋升的 drafts、疑似红线内容混入库；重点检查 AI 最常读的入口文件（根索引、profile 类背景文件），它们错了后面全错

**体检报告骨架**（每次体检按此出，发现项写「实际结果」，不许报喜不报忧）：

    # 知识库体检报告 {日期}
    ## 结构层（对账脚本输出）
    - 索引↔文件不一致：{条数+明细}
    - 断链 / 孤儿引用：{条数+明细}
    ## 内容层
    - 过时结论：{文件+具体位置}
    - 前后矛盾：{文件对}
    - 积压 drafts：{文件+放了多久}
    - 疑似红线内容：{文件+实际情况}
    - 入口文件（根索引 / profile）状态：{一句话}
    ## 建议动作
    - {按优先级列动作}

Why：凡是手工记账必然漂移。对账的本质是守住账实一致：索引说有什么，磁盘上就有什么，AI 读到的和实际存在的一致。

## 纠偏即规范

你纠正过 AI 一次的说法（比如某类文件必须放哪、某个术语的确切含义），当场写成规范文件进索引，AI 下次不再犯。原则：**重复性知识零容忍**——第二次遇到就固化成文档或脚本，不靠记忆。

## AI 主动回填

协作中产生的新理解（新证据、新解释、跨主题关系），AI 识别后**提议**回填到对应文件，用户确认才写。纪律：

- 写回的重要结论**链接回来源文件**（文件名一字不差）；引用时**原话与推断分开标注**
- 三级判断：已有内容只链接 → 补充旧结论就更新原页 → 跨主题独立判断才新建页
- 风格特征也是可回填的理解——攒了新写作样本或发现 AI 表达不合口味时，提议迭代 `style/` 三件套（同 BUILD 纪律：提议 + 逐条确认，绝不自动生成风格画像）

## 项目完结提炼

产品线结束或阶段性完结时：

1. 提炼前先 commit 一次原始项目域——动手前要有回滚点
2. 剔除 🔴 级内容（归档区也不收红线；红线内容物理隔离存库外）
3. `work/{{产品线}}/` 整体移入 `archive/` 原样冻结（子目录索引一并冻结，archive/ 不回流 work/）
4. 可复用的方法论（需求拆解模式、设计规范、踩坑记录）提炼汇入 `knowledge/`
5. Recent 登记一行

这是知识库对经验资产最大的复利——每个项目结束都沉淀为可复用的知识，下个项目从上一个的肩膀起步。

## 双 AI 对抗审查（重要产出定稿前可选）

让两个立场相反的 AI 各审一遍：正方验证目标是否达成、逻辑是否自洽；反方专职挑刺找漏洞、找反例。两边结论交叉看再定稿。实现方式：两个不同工具，或同一工具的两个会话（一个指令「验证它」，一个指令「推翻它」）。不必事事双审——日常笔记和随手存档单 AI 足够，双审留给要发给别人的东西。注意：双审意味着内容会发给第二个 AI——外发动作，先确认符合安全口径再用。

## 换机迁移

说「迁移知识库」（换电脑）时按此走：

1. **迁移清单打包**：仓库本体（Git 已含全部文本内容）+ 配置（AI 工具与 skill 的安装包/目录）；**凭证类敏感项（token、密钥、账号配置）单独保管，绝不打进迁移包**
2. 图片不在 Git 里（`.gitignore` 排除了 `**/assets/`）——assets/ 目录单独打包，通过认可的方式同步
3. 新机还原：clone 仓库 + 放回 assets/ + 重装工具与 skill
4. 逐项验证：跑对账脚本 + 背景测试（问「我是做什么的」），两项都过才算迁移完成

## 成长触发条件（命中 → 建议养护动作，不是升级）

- 库内文件总数 > 30 → 建议做一次 30 天体检
- Recent 区攒满 20 条 → 建议收编进正文清单（顺手动作）
- 用户抱怨「找东西难」「又乱了」→ 先跑对账脚本定位，再决定是否体检
- 出现疑似红线内容 → **优先处理**：先拦（不入库、不登记）、提醒用户确认安全口径、移出库（不入 Git、不入索引，最稳妥存库外），处理完再谈其他

触发条件的检查是顺手的——体感优先，数字兜底。命中时对用户说：库该养护了，说「体检」我带你过一遍。建议即可，不催不代决定。

## 养护收尾动作（每次做完必做）

1. Recent 登记本次养护（一行：日期 + 动作名 + 一句话）
2. 有 Git 则 commit——养护值得一个存档点
3. 跑一遍对账脚本，报告归零或记录遗留项
4. 重做一次背景测试——养护不能把「AI 认识你」弄丢

## 继续长大

需要更深的单项目/团队级 context 管理能力（多项目并行、产品上下文工程）时，配合 context-engineer 使用（GitHub 搜 LeeFinn2025/context-engineer）。kos-starter 管起步和日常，context-engineer 管深耕，两者不冲突。切换前建议先做一次体检，把基础打牢再上强度。
