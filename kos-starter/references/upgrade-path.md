# upgrade-path — Mode 3 GROW 升级路径 + 体检

> 触发：「升级知识库」「体检」「知识库乱了」，或 Mode 2 的成长触发条件命中。
> 原则：四个台阶每一步都独立可用，随时停下。升级是「把现有内容归类挪进更好的结构」，不是推倒重来。

## 台阶总览

| 时点 | 做什么 | 本章位置 |
|---|---|---|
| 第 0 天（30 分钟） | 最小版：文件夹 + 根索引 + AI 工具 | ✅ 已建成（Mode 1） |
| 用 2 周后 | 四区目录 + 敏感度分级 + Git 私有仓库 | 台阶 1 + 台阶 2 |
| 用 1 个月后 | 对账脚本 + 事件驱动对账 + 30 天体检 | 台阶 3 |
| 用 3 个月后 | 风格层三件套 + 双 AI 对抗审查 + 项目完结提炼 | 台阶 4 |

时间点是建议值，实际以成长触发条件为准（文件 > 30 / 用满 2 周 / Recent 满 20 / 抱怨找东西难 / 出现疑似红线内容）。用户喊「升级」时，先对照此表定位当前在哪级，缺哪级补哪级，不跳级。用户问「我该升级吗」：先报四台阶位置，再问一句「最近找东西费劲吗」——体感比日历准。各级台阶之间，日常照旧走 Mode 2 入库——升级是一次性动作，不改变日常习惯。

## 升级前检查清单（每级台阶动手前过一遍）

- [ ] Recent 区已收编（攒满 20 条的先收进正文清单）
- [ ] 没有未登记的孤儿文件（有就先补登记）
- [ ] 已用 Git 的话先 commit 一次——升级是重大变更，要有回滚点
- [ ] 与上一台阶的间隔够（对照总览表，不跳级）

## 台阶 1：四区改造（约 1 小时）

**什么时候值得做**：一个平铺文件夹开始装不下你的工作——项目笔记和行业收藏混在一起、这条产品线和那条产品线的文档互相污染时。不值得做：文件不多、主题单一，最小版够用就别动。

**四区一览**：

| 区 | 装什么 | 特点 |
|---|---|---|
| `work/{{产品线}}/` | 项目工作 | 按产品线隔离，项目完结整体归档 |
| `knowledge/` | 方法论、设计规范、竞品档案、行业认知 | 跨项目复用 |
| `style/` | 你的思维/表达/审美偏好 | AI 分身风格种子，始终加载（台阶 4 才填充内容） |
| `archive/` | 完结项目的整体归档 | 终态冻结，不套三层；方法论精华提炼入 knowledge/ |

三层生命周期（`drafts/` → `workspace/` → `context/`，知识只升不降）只套在 `work/` 与 `knowledge/` 两个内容区内部；`style/` 是扁平风格文件，`archive/` 是终态归档，不套三层。

四区不是齐步走：先建你用得着的区，其余留目录 + 一行种子索引，内容长出来再填。

**改造原则：内容比结构重要**——现有文件按区归类挪进去，不推倒重来、不改写内容。暂时为空的区留目录 + 一行种子索引即可，不造空架子装样子。

**操作**：

1. 盘点现有文件，逐个问「这属于哪个区」；拿不准的进该区 drafts 类目录
2. 用 `templates/AGENTS-full.md` 重写根索引，替换全部 `{{占位符}}`
3. 每个区建一份 AGENTS.md 子索引（结构参考根索引，越往下越具体：文件清单、区内规矩）。索引的两种合法形态此时一并写进规矩：**逐文件白名单**（只列出者可见，默认形态）与**目录级索引**（目录行声明整目录可见，AI 可在该目录内自由检索）——库小的时候全用白名单；某些目录文件多、更新频、当参考集用（竞品素材、行业报告这类成品参考集）时，再给它开目录级索引，免逐文件登记的维护成本
4. 挪动完成 → 逐区核对（索引列的 vs 实际存在的）→ Recent 登记本次改造

**迁移对照示例**（AI 逐文件带着用户过，每问一次「这个去哪」）：

| 现有文件 | 去处 | 依据 |
|---|---|---|
| profile.md（岗位与项目背景） | `knowledge/context/` | 跨项目复用的个人工作背景 |
| methods/ 下的方法论笔记 | `knowledge/context/`（一个文件一个领域） | 通用知识，跨项目复用 |
| notes/ 里的行业文章、竞品素材 | `knowledge/drafts/`，消化后升 context | 通用知识，拿不准先进 drafts |
| {{某产品线}}的项目笔记、方案素材 | `work/{{产品线}}/drafts/` | 项目工作，按产品线隔离 |
| 读了还没消化的收藏 | `knowledge/drafts/` | 拿不准进 drafts |

## 台阶 2：敏感度 + Git（约 30 分钟）

**三级定义（统一口径）**：

| 级别 | 含义 | 落地 |
|---|---|---|
| 🟢 | 可公开（公开行业文章收藏、已对外发布的内容） | 正常进 Git，可推远程 |
| 🟡 | 公司工作内容（**默认级**） | 照常进 Git，但远程仓库必须**私有**，仅限工作需要的人访问，永不对外公开 |
| 🔴 | 红线机密 | 不入 Git（`.gitignore` 排除）+ **不入索引**（对 AI 不可见）；最稳妥是物理隔离——存在知识库之外 |

两句诚实提醒，讲给用户听：

1. `.gitignore` 只管 Git，管不住 AI 读文件系统——🔴 内容除了排除出 Git，还不能登记进任何索引（未索引对 AI 不可见），最敏感的直接存库外物理隔离。索引规则是纪律约束，不是技术隔离
2. 🟡 是要进私有远程的，别误加进 `.gitignore`

**操作**：

1. **载体确认（动手前第一步）**：确认库推远程用的载体是公司认可的——有公司内网 GitLab 或公司指定仓库的优先用公司载体；公司无管控时，GitHub / Gitee（代码托管平台，相当于你的私有云盘）建**私有**仓库仅作替代选项。Mode 1 Step 0 已确认过的，复核一遍即可
2. `git init`（初始化版本管理，让这个文件夹开始被 Git 跟踪）并关联私有远程
3. 写 `.gitignore`（告诉 Git「这些文件永远别跟踪」的排除清单），示例几行：

   ```gitignore
   # 🔴 红线机密，永不进 Git（同时不入索引；最稳妥存库外）
   **/_private/
   # 图片不入 Git——防止仓库被撑爆，换机走公司认可方式单独同步
   **/assets/
   ```

4. 库内现有文件过一遍敏感度逐个标级；核心经营数据、薪酬信息、未公开的合作与商务条款一律 🔴（不入 Git、不入索引，最稳妥存库外）
5. 首次 commit + push（push = 把本地记录上传到远程备份），验证在另一台电脑能完整恢复

**内容默认分级速查**（拿不准时问用户，不替用户定密级）：

| 内容 | 默认级别 |
|---|---|
| 公开行业文章收藏、已对外发布的内容 | 🟢 |
| 工作文档、项目细节、方案、PRD | 🟡（默认级） |
| 核心经营数据、薪酬信息、未公开合作与商务条款 | 🔴（不入 Git + 不入索引，最稳妥存库外） |

Push 前确认两件事：远程载体是公司认可的吗？仓库是 Private 吗——任一不过，后面全白做。

Why：Git 是后悔药（每次修改可回滚、搞砸可回退）+ 换机不丢。🟡 是默认级，意味着「库里的东西默认就是公司工作内容」——私有远程是底线，一次误推公开就是事故，且互联网有记忆。

## 台阶 3：对账脚本 + 30 天体检

**对账脚本（让 AI 现场写）**：让 AI 当场写一个只读检查脚本，语言不限（用户环境能跑即可，PowerShell / Python / Bash 都行），核对四件事：

1. 索引列的文件都存在
2. 存在的文件都在索引里
3. 断链：索引或正文引用了不存在的文件
4. 孤儿引用：没有任何索引指向的文件

脚本只输出报告，不改任何文件——修不修、怎么修，人决定。脚本存进库（如 `tools/` 目录）并登记索引，之后复用。

**脚本自检（写完必做，防误报漏报）**：临时造两个测试项——库里放 1 个不登记索引的孤儿文件，索引里写 1 个不存在的文件名——跑一遍脚本，两项应双双出现在报告里；验证通过后删掉测试项。小白没有代码审计能力，这步就是脚本的可信度证明——拿着未经自检的报告去「当场修」，比不修还危险。

**事件驱动对账**：每批操作（入库、迁移、清理）收尾时跑一遍脚本，发现项当场修。不攒大扫除——攒到月底的账没人对。

**30 天体检（两层）**：

- 结构层：跑对账脚本，看报告处理发现项
- 内容层：人工 + AI 一起过——过时结论、前后矛盾、断链积压、该晋升没晋升的 drafts、敏感度误放（🟡 内容出现在 🟢 文件、疑似红线内容混入库）；重点检查 AI 最常读的入口文件（根索引、profile 类背景文件），它们错了后面全错

**体检报告骨架**（每次体检按此出，发现项写「实际结果」，不许报喜不报忧）：

    # 知识库体检报告 {日期}
    ## 结构层（对账脚本输出）
    - 索引↔文件不一致：{条数+明细}
    - 断链 / 孤儿引用：{条数+明细}
    ## 内容层
    - 过时结论：{文件+具体位置}
    - 前后矛盾：{文件对}
    - 积压 drafts：{文件+放了多久}
    - 敏感度误放：{文件+实际情况}
    - 入口文件（根索引 / profile）状态：{一句话}
    ## 建议动作
    - {按优先级列动作}

Why：凡是手工记账必然漂移。对账的本质是守住账实一致：索引说有什么，磁盘上就有什么，AI 读到的和实际存在的一致。

## 台阶 4：进阶机制（每个独立可用，按需启用）

**双 AI 对抗审查**（何时用：重要方案、文档定稿前）
让两个立场相反的 AI 各审一遍：正方验证目标是否达成、逻辑是否自洽；反方专职挑刺找漏洞、找反例。两边结论交叉看再定稿。实现方式：两个不同工具，或同一工具的两个会话（一个指令「验证它」，一个指令「推翻它」）。不必事事双审——日常笔记和随手存档单 AI 足够，双审留给要发给别人的东西。注意：双审意味着内容会发给第二个 AI 工具——这是外发动作，先确认符合公司安全口径再用。

**风格层**（何时用：想让 AI「像你一样」说话做事）
把决策习惯、表达偏好、审美标准写成 `style/` 下三个文件：`thinking.md`（怎么想问题）、`communication.md`（怎么说话）、`taste.md`（什么是好）。根索引声明「style/ 始终加载」。
流程五步：①喂样本（你的周报、邮件、评审意见）→ ②AI 提炼特征（决策模式 / 表达习惯 / 审美倾向）→ ③AI 提议具体条目 → ④你逐条确认，删掉不认可的 → ⑤写入并登记索引。绝不自动生成人格——每一条都得你点头。

**项目完结提炼**（何时用：产品线结束或阶段性完结时）
把 `work/{{产品线}}/` 整体移入 `archive/` 原样冻结（先剔除 🔴 级内容——归档区也不收红线）；可复用的方法论（需求拆解模式、设计规范、踩坑记录）提炼汇入 `knowledge/`。这是知识库对经验资产最大的复利——每个项目结束都沉淀为可复用的知识，下个项目从上一个的肩膀起步。提炼前先 commit 一次原始项目域——动手前要有回滚点。

## 台阶收尾动作（每级做完必做）

1. Recent 登记本次升级（一行：日期 + 台阶名 + 一句话）
2. 有 Git 则 commit——升级值得一个存档点
3. 已有对账脚本（台阶 3 起）就跑一遍；更早的台阶手工逐区核对
4. 重做一次 Mode 1 Step 5 的背景测试——升级不能把「AI 认识你」弄丢
